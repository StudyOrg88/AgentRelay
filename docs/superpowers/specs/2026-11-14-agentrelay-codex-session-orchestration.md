# AgentRelay Codex Session Orchestration

Date: 2026-11-14

## Purpose

AgentRelay is a minimal personal workflow for handing one GitHub Issue between Codex sessions on the user's configured local or SSH-connected projects. Codex Desktop owns remote session creation and execution. AgentRelay supplies the role decision, task handoff instructions, and the small amount of state needed to reconnect the Issue to its Codex thread.

## User and scope

- The only target user is the repository owner using Codex Desktop for personal development.
- The MVP targets GitHub.com only; normalize repository identity as `github.com/<owner>/<repository>` (case-insensitive owner/repository, with HTTPS/SSH remote syntax normalized). GitHub Enterprise Server hosts are unsupported and must fail closed rather than collide with github.com repositories.
- The handoff file provides one active orchestration slot per selected target clone's Git common directory. It does not provide a global lock across target repositories or separate clones of the same GitHub repository. The user must not run concurrent Orchestrator workflows across those handoff slots.
- The MVP can handle Issues in any GitHub repository. AgentRelay is the orchestration tool/source repository, not implicitly the task target. For each Issue, the user selects an Orchestrator project whose canonical `origin` matches the Issue URL repository; its Git object database is the only one used for fetch and Acceptance verification. Worker and Reviewer projects must also be clones/worktrees of that same target repository. A mismatch at any role blocks before task-file access or GitHub evidence is used for verification.
- Before using AgentRelay for a target, the user clones that target repository onto every participating device and manually registers each intended base project in Codex Desktop with its host and path. AgentRelay does not clone repositories, configure SSH hosts, or register Codex projects.
- The merge-only Controller is launched from the AgentRelay tool/source repository, but must accept the selected target repository path explicitly. The Orchestrator/Controller execution host must directly access both the Controller project and the target clone path. Its GitHub working directory, fetch/object database, and `GitAcceptanceVerifier` root must all be that target project; the tool/source repository is never substituted implicitly. Worker and Reviewer may run on other configured SSH hosts. If the target clone is available only on another host, pause; Phase 1 does not add remote Controller execution.
- Superpowers is a required Worker/Reviewer dependency. Both roles require an actual workspace independent from the selected base/Orchestrator workspace and from each other. `using-git-worktrees` may detect/reuse an already isolated Worktree or use native/Git tooling to create one when needed; a new Worktree per Chat is not required. The user must authorize the necessary isolated-workspace operations for these roles before dispatch; the prompt must state that this task is authorized to use an isolated workspace. This does not bypass Codex permission prompts or sandbox policy. In-place fallback is forbidden for both roles. If the skill is unavailable, authorization/permission is denied, the user declines, identity is shared, or initialization would modify the base worktree (including `.gitignore`), pause/return `BLOCKED`. AgentRelay never implements its own Worktree fallback or manager.
- The user selects a target project from the current `list_projects` results for each Worker or Reviewer dispatch; no separate device registry is maintained for the primary workflow.
- A configured Codex project is resolved through the session-management tools. `environment: local` means the selected project's configured host; it does not imply the current computer.
- Every remote Worker/Reviewer project selected for a role must be a user-prepared clone/base project registered in Codex Desktop; Worker and Reviewer may select the same base project if Superpowers establishes distinct actual workspaces.
- Windows, Ubuntu, and macOS may be used when present in the Codex project's host catalog. This is not a promise of standalone AgentRelay runtime support on each OS.
- No independent AgentRelay service, daemon, queue, database, multi-user support, or autonomous machine discovery is introduced.

## Responsibilities

Codex Desktop session-management tools own remote execution:

- `list_projects` discovers configured projects and their host/path identities.
- `create_thread` creates a new Codex Chat on the selected project's configured host and sends the task instructions as its initial message.
- `read_thread` (and an available wait operation when useful) reads the created thread by `threadId` and `hostId`.

AgentRelay owns only the workflow decisions and durable association:

- Read current GitHub Issue/PR evidence and decide whether the next role is Worker, Reviewer, Orchestrator/human input, or complete.
- Ask the user to select a project from the current Codex project list for the chosen role; stop if project identity is ambiguous.
- Construct a scoped initial prompt naming the Issue, role, relevant findings/acceptance scope, and required report format.
- Record the Issue, role, project identity, `threadId`, `hostId`, and last observed status so a later Codex session can resume observation.
- After a terminal thread status, inspect the returned response, reread GitHub, and only then select the next step.

AgentRelay does not launch or manage a remote Codex process itself on the primary path.

## Project selection and local state

For a new Issue, call `list_projects` and have the user select the Orchestrator project bound to the target repository; show enough identity to distinguish projects by host, name, and path. Resolve the selection to the exact returned `projectId` and `hostId`, then verify its canonical `github.com/<owner>/<repository>` identity matches the Issue URL before deriving the handoff path, reading/writing handoff state, or doing any target-repository Git/GitHub verification. GitHub.com HTTPS/SSH remote forms normalize to the same identity; any other host is unsupported. The selected target clone and AgentRelay Controller project must both be directly accessible on the Orchestrator/Controller execution host. Store the handoff under the validated target clone's Git common directory. On recovery, use the saved Issue URL, repository identity, and project identity to re-resolve and revalidate the same project; do not silently select or switch projects. At each new role dispatch, call `list_projects` and have the user select the Worker/Reviewer base project. Verify its canonical origin before task-file access. Worker then follows target repository instructions (including `AGENTS.md`) before coding; Reviewer reads only the issue, approved specification/plan, repository review instructions, and code needed for read-only review. `environment: local` is interpreted according to the selected project's configured host, not as an assertion that it runs on the current physical device. The AgentRelay source repository may differ and is never implicitly used as target or verifier object database. Worker and Reviewer may execute on other configured SSH hosts.

The local state is one small, versioned JSON file per target clone Git common directory, containing one active handoff: canonical Issue URL and repository identity; workflow `phase`; `threads.worker` and `threads.reviewer` records, each retaining project identity, `threadId`, `hostId`, actual workspace evidence, and last observed status; a `verification` object with `workerReportedSha`, `githubHeadSha`, `githubBaseSha`, `fetchedSha`, `acceptanceTargetSha`, `reviewerReviewedHeadSha`, `reviewerReviewedBaseSha`, `expectedMergeSha`, and `mergeCommitSha`; `pauseReason` and `pausedFromPhase` when paused; and update time. The minimal phases are `worker_selecting`, `worker_creating`, `worker_active`, `reviewer_selecting`, `reviewer_creating`, `reviewer_active`, `merge_ready`, `merging`, `completed`, and `paused`. Before calling `create_thread`, atomically write the relevant `*_creating` phase and selected project identity to that role's thread record with a null thread ID. After receiving both thread identifiers, atomically update that record and transition to the matching active phase. Before the merge operation, atomically persist `phase: merging` and `verification.expectedMergeSha`. On pause, preserve the prior phase and a concise reason code. The file contains no prompt transcript, credentials, or copied GitHub comments. It is a recovery pointer, not the source of truth for GitHub or thread contents; all external state and evidence must be reread during recovery.

## Normal flow

1. The user starts the AgentRelay orchestration workflow in Codex Desktop with one canonical GitHub Issue URL.
2. For a new handoff, Codex calls `list_projects`, asks the user to select the Orchestrator project, resolves the exact `projectId`/`hostId`, and verifies its canonical `github.com/owner/repository` identity matches the Issue repository. Only then may it derive the target repo Git common dir handoff path and read/write state. The target clone and Controller project must be accessible on this Orchestrator/Controller execution host. For recovery, it uses saved Issue/repository/project identity, revalidates that same project, and never silently switches projects.
3. Codex reads GitHub and selects the next role using the existing AgentRelay task-entry and role skills.
4. Codex calls `list_projects`, asks the user to select the Worker or Reviewer base project, resolves its exact `projectId`/`hostId`, and verifies canonical `origin` matches the Issue repository before reading/modifying task files or creating a thread. It confirms the user has authorized isolated-workspace operations, atomically saves `*_creating` plus selected project identity, then calls `create_thread` with the scoped initial prompt. The prompt explicitly says isolated work is authorized, requires `using-git-worktrees`, and forbids in-place fallback. Worker follows repository instructions (including `AGENTS.md`) after identity verification; Reviewer reads only material required for read-only review. A mismatch blocks before handoff mutation or task-file access.
5. Once both `threadId` and `hostId` are returned, Codex saves them and changes the phase to `*_active`; it then observes that same thread. It never creates a replacement merely because a read temporarily fails.
6. Before the first Worker dispatch, an Issue without a PR remains eligible for normal routing. While the Worker thread is active, continue observing that same thread. After a terminal Worker thread, read its report and GitHub state. If implementation/a PR was expected but no matching PR exists, pause with `worker_pr_missing`; do not create another Worker thread because the PR is absent. A no-code-change report routes to Orchestrator/human to apply existing Issue lifecycle rules; it does not invent a no-PR completion rule. A failed Worker report pauses and does not dispatch Reviewer. Successful implementation reports include matching PR URL, full commit SHA, branch name, tests run/results, actual change summary, Acceptance-related evidence, and workspace evidence. Confirm the PR belongs to the Issue repository and is actually associated with the Issue. Once a PR exists, read its full head/base SHA, base ref, and repository `default_branch`; require base ref to equal default branch. Validate the ref using `git check-ref-format --branch` and pass as a distinct Git argument, never shell-concatenated. Fetch head/base refs into the selected target repository's Git object database used by `GitAcceptanceVerifier`, without checking out or changing the Orchestrator working tree. A fresh GitHub read must still match fetched full SHAs and Worker-reported head SHA; incomplete history, fetch error, repository mismatch, or SHA mismatch blocks further progress.
7. The PR base ref must equal the GitHub repository's configured default branch, used as the canonical target-branch policy; an unknown default or any other base ref is `BLOCKED`. `GitAcceptanceVerifier` reads the Acceptance record and code ancestry at PR head, and trusted Acceptance v1 schema/policy from the verified PR base SHA. It does not rely on checked-out branch or working-tree Acceptance files. A temporary acceptance worktree is not required unless a future verifier adds working-tree-dependent checks. Any PR modification of Acceptance schema/policy is blocked until a machine-verifiable approval contract exists; never use the PR's changed rules to validate itself.
8. Before Reviewer dispatch, the Orchestrator verifies current PR head/base SHAs again. It selects a target-repository base project, which may be the same Codex project selected for Worker. Superpowers `using-git-worktrees` may reuse an existing isolated workspace or establish one; new creation is not assumed. Before review preparation, Reviewer verifies `origin`, obtains fresh GitHub PR HEAD/BASE, and prepares its isolated workspace at the exact PR HEAD (for example, fetch the PR head object/ref then checkout/detach that SHA). This is preparation, not the read-only review. Verify workspace identity differs from both the selected base/Orchestrator workspace and Worker; identity is `(hostId, canonical physical workspace path)`, same-host aliases resolve to the same path, and shared Git common directories are allowed. Verify `HEAD == current GitHub PR HEAD`, base commit object exists with `git cat-file -e <base-sha>^{commit}`, and working tree/index are clean. The review range is exactly Base=current PR base SHA and Head=current PR head SHA. Once read-only review begins, do not change HEAD, index, branch state, or tracked/untracked workspace contents. Apply Superpowers Code Reviewer standards directly without `requesting-code-review` sub-agent dispatch. After review, re-read GitHub and repeat HEAD/BASE/object/clean checks; report exact full SHAs plus workspace evidence. If Superpowers falls back to a shared original workspace, setup requires modifying the base repo (including `.gitignore`), or identity/SHA/cleanliness cannot be established, return `BLOCKED`, never PASS.
9. After the Reviewer thread is terminal, Codex rereads GitHub. `PASS` is usable only when both `reviewed_head_sha` and `reviewed_base_sha` equal the current full PR head and base SHAs. A change to either invalidates Acceptance and Reviewer evidence; `FAIL`, `BLOCKED`, an unusable report, or changed head/base pauses the MVP and prevents merge. Automatic Worker remediation loops are deferred.
10. Before merge, the Orchestrator performs a fresh GitHub read and revalidates PR identity/state, current head and base SHAs, target repository, local fetched objects, Acceptance result, Reviewer head/base SHAs, required checks, and existing Merge Bot gates. It atomically saves `phase: merging` and current full PR head as `expectedMergeSha`, then invokes the merge operation with that SHA as a server-side precondition. Prefer `gh pr merge --match-head-commit <SHA>`; if unsupported, fail closed. GitHub's merge precondition protects HEAD, not base, so base SHA must be rechecked immediately before the call. Any head/base change invalidates prior evidence and requires fresh verification/review. If Merge Queue is enabled, queue acceptance is not completion: keep rereading GitHub until `merged` is true and a full `merge_commit_sha` is present. For uncertain results or resume in `merging`, reread GitHub first; confirmed merged means finish; confirmed unmerged means rerun all gates before another attempt; unreadable state means pause without retrying.
11. After an acknowledged or recovered merge, reread GitHub and confirm the PR is merged, a full merge commit SHA is present, and the Issue lifecycle is complete. Save GitHub's resulting merge commit SHA as `verification.mergeCommitSha`, then mark local state `completed`.

## Recovery and failure behavior

- If the parent orchestration Chat stops, a later Codex Chat can load the local handoff state and call `read_thread` with the saved `threadId` and `hostId`; the remote Chat continues independently.
- Each target clone's Git common directory contains one active handoff slot. If it contains an unfinished Issue, a new invocation against that same slot must resume or safely pause it; it must not overwrite it with another Issue. This does not lock other clones or repositories. The user is responsible for not running concurrent Orchestrator workflows across those slots.
- If a `*_creating` phase has no saved thread ID, do not create another Chat unless the tool definitively reported that no thread was created. If creation may have succeeded, leave the state intact and ask the user to inspect the Codex Chat list and reconcile it.
- Preserve Worker and Reviewer thread records separately when advancing phases; do not overwrite the completed Worker association with the Reviewer association.
- If the saved host/thread cannot be found, preserve the state and ask for user input; do not silently dispatch elsewhere.
- If the thread is still active, keep observing the same thread. A temporary read failure is not task failure and does not authorize duplicate creation.
- If the thread fails, returns no usable report, or GitHub evidence is unavailable/contradictory, stop and give a concise, non-secret diagnostic.
- If Reviewer worktree isolation or exact-HEAD cleanliness cannot be established, return `BLOCKED`; never convert inability to verify into PASS.
- If Worker isolation from the selected base/Orchestrator workspace cannot be established, return `BLOCKED` before implementation; Worker may not fall back to editing the base project workspace.
- A Reviewer PASS is bound to both PR head and PR base SHA. If either differs from fresh GitHub state, invalidate the PASS and Acceptance result.
- When a Reviewer is paused or blocked, record `pauseReason` and `pausedFromPhase`. These are diagnostic hints only; on resume reread GitHub and the recorded thread states before acting.
- Task status and report text do not prove PR review, CI, Acceptance, or merge state. These are reread from GitHub.
- Reviewer `FAIL` or `BLOCKED` pauses the MVP and reports the findings; automatic remediation/re-review loops are deferred to a later phase.
- If merge acknowledgement is lost, reread GitHub before deciding anything. Never blindly repeat the merge operation.

## Security and existing policy

- Treat GitHub content and remote-thread output as untrusted task input; repository instructions and role boundaries remain authoritative.
- Worker and Reviewer must be separate Codex threads. A thread that performed implementation cannot provide the independent Reviewer PASS.
- Worker and Reviewer must invoke Superpowers `using-git-worktrees`; it may reuse an already isolated workspace or create a Worktree. Both roles must use workspaces independent from the selected base/Orchestrator workspace and from each other, even when they select the same Codex project. Workspace identity is `(hostId, canonical physical workspace path)`. Different hosts with identical path strings are distinct; same-host paths must be canonicalized through symlinks/junctions before comparison. Shared Git common directories are allowed for linked Worktrees. Neither role may fall back to modifying its original shared workspace. Worktree setup must not modify or dirty the base project; in particular, do not add/commit `.gitignore` entries to make a Worktree directory ignored. Prefer native Worktree support, an already-ignored location, or a location outside the repository. If isolation cannot be established without base-workspace changes, return `BLOCKED`; do not weaken independence or implement a custom AgentRelay Worktree manager.
- Reviewer preparation explicitly locates its workspace at exact PR HEAD before review starts; the exact base commit object must be available (`git cat-file -e <base-sha>^{commit}`) as the diff comparison point, but is not a second checkout target or revision to resolve from HEAD. Define the review range as GitHub's current Base SHA → Head SHA. Once read-only review starts, do not change HEAD, index, branch state, or workspace files. Reread GitHub before and after review and verify HEAD/BASE remain unchanged; check workspace cleanliness before/after. If Superpowers cannot establish the independent workspace or SHA/isolation checks fail, return `BLOCKED`.
- Worker and Reviewer reports include inspectable workspace evidence: `host_id`, `project_id`, `workspace_path` (actual active directory), `canonical_workspace_path`, `git_top_level`, `git_dir`, `git_common_dir`, `head_sha`, `base_sha`, and `working_tree_clean`, with before/after snapshots where applicable. Orchestrator compares identity using only host plus canonical physical workspace path and independently checks SHA/cleanliness. `git_top_level`, `git_dir`, and `git_common_dir` are supporting evidence, not substitutes for workspace identity; equal or different common directories alone do not prove independence.
- The Reviewer Chat directly applies the Superpowers Code Reviewer standards/template (including `skills/requesting-code-review/code-reviewer.md` where available). It must not invoke the `requesting-code-review` sub-agent dispatch workflow or create another Reviewer layer. The AgentRelay-created Reviewer Chat is the independent reviewer.
- Worker prompts state the task goal, approved scope/acceptance criteria, delivery authority, and structured report format; they do not redefine engineering methods. Superpowers provides development method: use `using-git-worktrees`, `test-driven-development`, `systematic-debugging` when diagnosing problems, `verification-before-completion`, and `finishing-a-development-branch` as applicable. Worker is authorized to create a branch, commit, push, and create/update a PR as required by the task, but never to merge. A successful implementation report is structured JSON with PR URL, branch, full commit SHA, tests/results, change summary, Acceptance-related evidence, and workspace evidence. Explicit no-code-change and failure reports state that outcome and reason. Report actual verification evidence rather than unsupported completion claims.
- Reviewer evidence remains bound to the exact reviewed PR head SHA, PR base SHA, target repository, and the existing Acceptance v1 contract.
- The SHA chain immediately before merge is exact: Worker report commit = freshly reread GitHub PR head = locally fetched head = Acceptance verification target = Reviewer `reviewed_head_sha` = expected PR head for merge; GitHub PR base = locally fetched base = Acceptance policy source = Reviewer `reviewed_base_sha`. If either PR SHA changes, earlier verification/review evidence is stale and must not authorize merge. The resulting squash/merge commit may have a different SHA and is verified afterward as GitHub's merge result.
- The Git repository used by `GitAcceptanceVerifier` must correspond to the canonical `github.com/owner/repository` in the Issue URL, regardless of where AgentRelay itself is hosted. GHES is not supported in this MVP. Verify the selected Orchestrator project's `origin` identity before deriving/accessing handoff state, task-file access, fetch, and merge; verify Worker/Reviewer project identity before task-file access. A mismatch blocks; never fetch PR refs into an unrelated object database. Tasks in any GitHub.com repository are supported when matching projects are selected.
- Controller and target clone must be accessible from the same Orchestrator/Controller execution host. The CLI is launched from the AgentRelay tool project and receives an explicit target repo path, which must resolve on that host to the selected clone whose object database is used by fetch and `GitAcceptanceVerifier`. Worker/Reviewer may run remotely. If only a remote Worker/Reviewer host has the target clone, pause; do not add remote Controller execution in Phase 1.
- The fetched PR object and required ancestry must be present in the same local Git object database used by the existing `GitAcceptanceVerifier`; fetching into some other clone is not sufficient. The verifier currently reads the Acceptance record using `git show <target-sha>:<path>` and verifies ancestry using explicit commit IDs, so fetching the target commit and required history is sufficient for its present Git-object-based checks; an isolated worktree is not needed for this verifier unless it later gains working-tree-dependent behavior.
- Acceptance v1 schema/policy authority comes from `docs/acceptance-schema-v1.json` and the repository's Acceptance policy at the exact PR base SHA, after verifying the base ref is the repository's configured default branch. The PR head's copy is never authoritative for validating that PR. If the PR changes the schema or policy, block unless the repository's existing explicit policy-change approval is verifiable; if the base SHA, target branch, or approval cannot be verified, fail closed. The verifier reads the trusted schema at the base SHA while evaluating the acceptance record and code ancestry at the target PR SHA.
- After fetching, reread GitHub and compare its current full PR head SHA to the Worker report and fetched SHA. Repeat that comparison immediately before merge. The merge operation must carry the expected PR head SHA as a server-enforced precondition; a pre-merge reread alone is insufficient because the head can change between the read and merge request. This precondition does not atomically lock PR BASE: base is reread immediately before merge, while existing branch protection and Merge Queue policies remain authoritative. If the GitHub operation rejects the expected SHA, do not retry with a refreshed SHA until Acceptance and Reviewer have both been rerun for that SHA.
- Existing required-check, current-HEAD, open/mergeable PR, and merge-bot gates remain fail-closed. No task response alone can authorize merge.
- Never put tokens, passwords, private keys, or other credentials in the initial prompt, local handoff state, or GitHub artifacts.
- Codex Desktop session tools are the executor; the standalone .NET Controller CLI does not gain access to them implicitly.

## Existing implementation disposition

The existing .NET Controller, Agent, SSH transport, and process supervision remain in the repository as a legacy/experimental execution path during migration. They are not prerequisites for the Codex Desktop primary workflow. Do not delete or maintain feature parity with that path as part of the minimal migration unless a separate decision requires it. Existing shared GitHub lifecycle and merge-policy code may be reused where practical.

The current `GitAcceptanceVerifier` is object-database based, but it reads the schema from the target PR commit. Implementation must change it to read the trusted schema/policy from the verified PR base SHA while evaluating the record and code graph at PR head. The current `GhMergeGitHubClient` invokes `gh pr merge ... --squash` without a head precondition; prefer adding `--match-head-commit <SHA>` and check the installed `gh` version, failing closed if unsupported. Worker and Reviewer rely on Superpowers `using-git-worktrees`; verify the plugin is available in each created Chat and worktree creation is permitted. AgentRelay verifies the resulting workspace identity and SHAs but does not prepare/register projects or manage worktrees.

## MVP phases

Phase 1 is the smallest complete normal path: user-prepared target clones registered as Codex base projects → Issue readiness → user-selected target repository project → Worker Chat (Superpowers worktree detection/reuse or creation + TDD/implementation/verification and authorized branch/commit/push/PR delivery) → target-repository fetch and Acceptance verification → separate Reviewer Chat (independent Superpowers workspace, exact PR HEAD + read-only Base-to-Head review) → final merge gates → merge and GitHub confirmation. Neither role may edit the base project to enable isolation; Reviewer FAIL/BLOCKED pauses; automatic remediation loops are deferred. One handoff slot exists per target clone Git common directory; no cross-clone global lock is provided.

Before implementation claims the normal path is complete, verify the selected Orchestrator project's canonical `origin` matches the chosen Issue repository, its default branch is the only trusted PR base, and base/head objects are fetched into the exact Git object database used by the verifier. The user must clone the target repository on participating devices and register the intended base projects in Codex Desktop; AgentRelay does not do this setup. Verify Superpowers is available to Worker and Reviewer Chats and worktree operations are permitted. In a manual Desktop test, both roles may start from the same base project; Superpowers may reuse a pre-isolated workspace or create a Worktree. Verify both actual role identities are distinct from the base/Orchestrator workspace and each other, and setup leaves the base project unchanged (including `.gitignore`). Verify Worker can deliver the requested branch/commit/push/PR and does not merge. Reviewer must verify origin, locate fresh PR HEAD/BASE, position its isolated workspace at exact HEAD, confirm the base commit exists (`git cat-file -e <base-sha>^{commit}`), and confirm clean state before review. Then check the review range is exactly Base SHA → Head SHA and that HEAD/index/branch/files remain unchanged during read-only review. Confirm GitHub HEAD/BASE, workspace identity, and clean checks before and after review; `reviewed_base_sha` must exactly equal the full GitHub PR base SHA. If Superpowers falls back to a shared workspace, setup modifies the base project, or identity cannot be verified, that role is `BLOCKED`; do not substitute thread separation for workspace isolation or add a custom AgentRelay Worktree manager. Also verify trusted-base Acceptance policy lookup and installed `gh` support for `--match-head-commit`.

Phase 2 may add automatic remediation/re-review loops and broader interruption scenarios. Phase 3 may improve reports and reduce user interaction. Thread-creation ambiguity protection, same-thread read recovery, SHA rechecks, and merge-outcome rereads remain required in Phase 1.

## Explicit non-goals

- Calling Codex Desktop session tools from the standalone `agentrelay-controller` executable; the merge-only CLI may still be launched by the Skill with an explicit target repository path.
- Building a new MCP server or remote session broker.
- Automatically deleting, cancelling, or replacing remote Chats.
- Supporting Issues without a user-selected project whose canonical `github.com/owner/repository` matches the Issue repository; GitHub Enterprise Server; global task locking across separate clone common directories; remote Controller execution when the target clone is inaccessible on the Orchestrator/Controller host; load balancing, elaborate retries, multi-user authorization, a separate device registry, or AgentRelay-managed worktree lifecycle.
- Automatically looping Reviewer FAIL back to Worker remediation in Phase 1.
- Removing the existing .NET Agent/SSH path in this migration.
- Claiming macOS runtime support for the legacy .NET Agent based only on Codex project availability.
